## 1. 项目概览

### 1.1 定位

GhostJ 是一个 **Java 实现的三端远程控制平台**，由三个独立运行的 JVM 进程组成：

- **Client** — 被控端，部署在目标主机，主动连接 Server
- **Server** — 中转 / 管理端，公网常驻，承担连接管理、消息转发、文件存储
- **Master** — 控制端，Swing 桌面 GUI，由操作人员使用

### 1.2 仓库结构

```

├── src/com/ghostj/
│   ├── client/         # 被控端
│   │   ├── cmd/        # 指令抽象：AbstractFunc、Command、AbstractProcessor
│   │   ├── conn/       # 与 Server 的连接管理
│   │   ├── core/       # 入口、Processor、ScreenSniffer
│   │   ├── func/       # 20+ 个 Func 实现（截屏/键鼠/录音/进程/文件…）
│   │   └── util/       # Out、Config、FileRW、PrtScreen
```

## 2. 整体架构

### 2.1 拓扑

```
                   ┌──────────────────────┐
                   │       Server         │
                   │  TCP 1033 (Client)   │
       ┌──────────►│  TCP 1034 (Master)   │◄───────────┐
       │           │  TCP 1035 (RFT)      │            │
       │           │  TCP 1036 (RFTX)     │            │
       │           └──────────────────────┘            │
       │                       ▲                       │
       │           HTTP        │                       │
       │  http://host/ghost/   │                       │
       │  （客户端用 RFT 上传   │                       │
       │   截屏/录音，Master   │                       │
       │   再通过 HTTP 取回）   │                       │
       │                                               │
┌──────┴──────┐   ┌──────┴──────┐                 ┌────┴──────┐
│  Client 1   │   │  Client 2   │   ...           │  Master   │
│ (被控端)    │   │ (被控端)    │                 │ (Swing)   │
└─────────────┘   └─────────────┘                 └───────────┘
```

### 2.2 数据流

**指令下行**（Master 发起 → 被控端执行）：

```
Master 输入框
   │ TCP 1034
   ▼
Server.HandleMaster.handleCommand()
   │ 解析：!cmd → server 内部；!!cmd → 转发到 focusedConn
   ▼
Server.HandleConn.bufferedWriter.write()
   │ TCP 1033
   ▼
Client.HandleConn 读取
   ▼
Client.Processor.start(cmd)
   │ 解析、匹配 AbstractFunc
   ▼
具体 FuncXxx.run()
   │ 执行（截屏/键鼠/录音/进程操作…）
   ▼
（可选）通过 RFT 把产物（图片/录音）上传到 Server 1035 端口
```

**消息回上行**（Client 输出 → Master 显示）：

```
Client 子进程 stdout
   ▼
Client.HandleConn 收集（FuncProcess 管理）
   ▼
TCP 1033 → Server.HandleConn
   ▼
若该 Client 是 focusedConn，则写到 Server 终端 + 通过 Out 广播给所有 Master
   ▼
TCP 1034 → Master.HandleConn
   ▼
Master.AddStringToConsole.add()
   │ 200ms 或 200 字符触发 flush
   ▼
Console JTextArea 显示
```

### 2.3 模式选择

- **客户端**已用**策略模式**重构：每个指令对应一个 `FuncXxx` 类，新增指令只需新建 Func + 在 `ClientMain.registerAllFunc()` 注册。
- **服务端**未做模式化：`TransCmd.handleCommand()` 是一个超长的 `switch` 块，承接所有 `!` 指令。
- **控制端**事件驱动 Swing：网络 I/O 在独立线程，GUI 更新走 `AddStringToConsole` 缓冲队列。

## 3. 通信协议

### 3.1 传输层

| 链路 | 协议 | 默认端口 | 配置项 |
|---|---|---|---|
| Client ↔ Server（控制信道） | TCP | 1033 | `port` |
| Master ↔ Server（控制信道） | TCP | 1034 | `master.port` |
| Client → Server（RFT 单向文件） | TCP | 1035 | `rft.port` |
| Client ↔ Server（RFTX 双向文件） | TCP | 1036 | `rftxPort` |
| Master → Server HTTP（取截屏/录音） | HTTP | 80 | `rft.httpRoot` |

### 3.2 报文结构

报文是**文本帧**，没有长度前缀。两种边界字符：

```
!<funcName> <arg1> <arg2> ... <argN>!
!<funcName> <arg1> <arg2> ... <argN>\n
```

服务端逐字符读取，遇到 `!` 或 `\n` 即视为一帧结束（`server_old/HandleConn.java:53-65`）：

```java
if((char)c=='!'){
    StringBuffer cmds=new StringBuffer("!");
    while((c=inputStreamReader.read())!=-1){
        if((char)c=='!') { cmds.append("!"); break; }
        if ((char)c=='\n') { cmds.append("\n"); break; }
        cmds.append((char)c);
    }
}
```

### 3.3 指令前缀

| 前缀 | 含义 | 处理位置 |
|---|---|---|
| `!cmd` | Server 级，服务端自己处理 | `TransCmd.handleCommand()` |
| `!!cmd` | Client 级，由 Server 透传给 focusedConn 执行 | `Client.Processor.parse()` |
| `#cmd` | Master ↔ Server 的内部控制协议 | `HandleMaster.handleCommand()` |

> **设计后果**：Master 输入未识别的 `!xxx`，会被 Server 默认转发给当前 focused Client，达到"未知即透传"的效果。

### 3.4 参数与转义

- 参数以**空格**分隔
- `Processor.parse()` 把 `%HOST_NAME%` 替换为本机名称
- 文件路径含空格时：`?` → 空格，`*` → `!`（仅 `FuncRFT` 内）

### 3.5 字符编码

历史上有过两套方案，最近的 commit `c600f88`（feat: disable character coding convert on client）把客户端简化为：

- **发送**：直接 `getOutToServer().write(msg)`，不做 UTF-8 ↔ GBK 转换
- **接收**：`new InputStreamReader(socket.getInputStream(), "GBK")`

服务端和 Master 全程使用 **GBK** 编码（因为承载方为中文 Windows 主机的可能性较大）。`fastjson` 仅用于个别复杂数据结构的局部序列化，**不是**整体消息封装格式。

### 3.6 握手流程

**Client → Server 握手**：

1. Socket 连接（30 秒超时），`client/conn/HandleConn.java:63-70`
2. Client 发送：`!info <name> c<version> <sysStartTime> <installTime>!`
3. Server 解析并登记，标记 `avai=true`，加入 `socketArrayList`
4. 若服务端为该客户端预设了重命名 / startup 任务，会发出 `!!name <newName>` / `!!cfg write` / 启动指令

**Master → Server 握手**：

1. Socket 连接到 `master.port`，`master/conn/CreateConn.java:25`
2. Master 发送：`#login <masterName> <password>`
3. Server 在 `HandleMaster.handleCommand()` 校验：
   ```java
   case "#pw":{
       if(ServerMain.masterPw.equals(cmd[1])){
           this.available=true;
           ServerMain.sendListToMaster();
       } else {
           addMsg("!passErr!");
           kill();
       }
   }
   ```
4. Master 上报自身属性：`#attri listenerMaster` / `#attri desktop` / `#attri screenShot`，Server 根据属性决定是否向其推送某些事件

### 3.7 心跳协议

| 链路 | 周期 | 探针 | 应答 | 超时处理 |
|---|---|---|---|---|
| Client → Server（客户端主动） | 30 秒 | `!alive!` | `#alive#\n` | 10 秒未收到，Client 自杀重连 |
| Server → Client（服务端轮询） | 240 秒 | `#alives#` | `!alives!` | success 标志未置位 → `killConn()` |
| Server ↔ Master | 60 秒 | `!alivem!` / `#alivem#` | 互相 ACK | 10 秒超时 → `kill()` |
| Master → Server | 10 分钟 | `#alivems#` | `!alivems` | 30 秒超时 → 弹回登录页 |

实现位于：
- `client/conn/CheckAliveTimer.java:21-37`
- `server_old/CheckAliveTimer.java:13-48`
- `server_old/CheckMasterAlive.java:11-58`
- `master/conn/CheckServerAlive.java`

### 4.3 关键 Func 详解

#### 4.3.1 FuncPrtScr — 截屏

- API：`java.awt.Robot.createScreenCapture()` + `javax.imageio.ImageIO`
- 参数：`!!scr <fileName> [szRate] [clRate] [w] [h] [x] [y] [colorFormat]`
  - `szRate`：分辨率压缩比（>1 缩小）
  - `clRate`：色彩压缩比（0~1，灰度化）
  - `colorFormat`：BufferedImage TYPE 常量，如 `2 = TYPE_USHORT_GRAY`
- 截完调用 `FileSender.sendFile()` 通过 RFT 上传，除非倒数第二个参数是 `nosend`
- 实现：`client/func/FuncPrtScr.java:86-100`、压缩逻辑在 `util/image/ImageConvert.java`

#### 4.3.2 FuncKMR — 键盘鼠标

- API：`java.awt.Robot`（`keyPress`/`keyRelease`/`mouseMove`）
- 子命令：
  - `!!kmr key p <vk>` — 按下
  - `!!kmr key r <vk>` — 释放
  - `!!kmr key t <vk>` — 按下再释放
  - `!!kmr mouse m <x> <y>` — 移动
  - `!!kmr -t:<ms> ...` — 持续时间
  - `!!kmr lock` / `unlock <clientName>` — 软锁定操作权限

#### 4.3.3 FuncProcess — 子进程管理

- 通过 `client/core/ProcessCmd.java` 包装 `Process`
- 子命令：
  - `!!proc new [name] [cmd]` — 默认 `cmd.exe`，启动后自动 focus
  - `!!proc bg [name] [cmd]` — 启动但不 focus
  - `!!proc focus <prefix>` — 切换 focus（后续未识别指令透传到此进程的 stdin）
  - `!!proc ls` — 列出所有子进程
  - `!!proc disc <prefix>` — 解除关联但不杀进程
- 配合 `FuncDefault` 实现"未识别指令 → 当前 focused 进程"的透传

#### 4.3.4 FuncRFT — 文件上传

- 路径转义：`?` → 空格、`*` → `!`
- 子命令：
  - `!!rft upload <localFile> <remotePath>`
- 调用：`FileSender.sendFileMethod(source, remote, taskId, ip, 1035)`
- 目录递归：`UploadDir()`

#### 4.3.5 FuncAudio — 录音

- API：`javax.sound.sampled.{AudioFormat, TargetDataLine, AudioSystem}`
- 格式：PCM 16-bit 44100 Hz 单声道
- 流程：开线 → `sleep(length)` → 停止 → 写入 `audio.wMASKav` → RFT 上传
  - 文件名带 `MASK` 是给 Server 端识别用，传输完成时去除（见 `server_old/FileReceiveEvent.java`）

#### 4.3.6 FuncRFE — 远程文件浏览

- 协议：Master 发 `!!rfe <op> [args]`，Client 用 `java.io.File` 遍历，返回格式：
  ```
  !reDir <path>|<name1>:<isDir>:<size1>|<name2>:<isDir>:<size2>|...
  ```
- 支持 `dir` / `cd` / `upload`（隐式调 RFT）/ `download` / `dsk`（列盘符）/ `del`

### 5.3 连接处理器

| 类 | 职责 |
|---|---|
| `AcceptConn` | 端口 1033 接受 Client；执行 IP 黑名单（正则）；为每个连接创建 `HandleConn` |

### 5.4 TransCmd — 指令派发中心

`server_old/TransCmd.java` 是服务端最长的类，包含所有 `!xxx` 指令的 switch case。完整列表见 [§7 指令参考](#7-指令参考)。架构上等同于"上帝类"，是后续重构的首要目标。

### 5.5 心跳与在线检测

```
CheckAliveTimer (240s) ─→ 遍历 socketArrayList
                           ↓
                       set success=false
                           ↓
                  发送 #alives# 给每个 Client
                           ↓
                  sleep 10ms 检查 success
                           ↓
                   失败 → killConn()
                           ↓
                  成功 → TagLog.addTag(name, "alive")

CheckMasterAlive (60s) ─→ 遍历 AcceptMaster.masters
                           ↓
                  发送 !alivem! 给每个 Master
                           ↓
                  10s 超时检查 alive 标志
                           ↓
                   失败 → kill()
```

### 5.6 TagLog — 在线时间追踪

`server_old/TagLog.java`、持久化到 `tagLog.txt`，格式：

```
hostname1:1709876543210 login,1709876573210 alive,1709876603210 alive;
hostname2:1709876600000 login;
.Server:1709876500000 login,1709876530000 alive;
.Master:1709876520000 login;
```

- 心跳成功一次记一条 `alive`
- 客户端首次连接记 `login`
- 服务停机时把所有在线 Client 标记一次 alive

数据由 Master 的 `OnlineTimeChart` 拉取并可视化。

### 5.7 文件接收：FileManager + FileReceiveEvent

- `FileManager`：维护当前 RFT 浏览目录（默认 `/files/`），支持 `getFileListString()`、`changeDir()` 等
- `FileReceiveEvent`：实现 `TaskEvent`，每次接收完成触发。文件存到 `rootPath + savePath + fileName`，并对 `.png` / `.wav` 文件**生成 HTTP URL 推送给具备 `screenShot` 属性的 Master**：
  ```
  http://39.100.5.139/ghost/<rootPath>/<savePath>/<fileName>
  ```
  Master 拿到 URL 后通过 HTTP 下载并显示。

### 6.6 控制台缓冲：AddStringToConsole

为避免每条消息都触发 Swing 重绘，`master/core/AddStringToConsole.java`：

- 内部 `StringBuffer buffer`
- 后台定时器 20ms 检查一次
- 满足任一条件即 flush 到 Console：
  - `buffer.length() >= 200`
  - 距上次写入 >= 200ms

## 8. 文件传输 RFT/RFTX

### 8.1 RFT（单向，1035）

**Client 侧调用**（`client/func/FuncRFT.java:34-59`）：

```java
File source = new File(params[1]);
String taskId = new Date().getTime() + "";
FileSender.sendFileMethod(source, remotePath, taskId,
                          HandleConn.ip, 1035);
```

**Server 侧**：

```java
fileReceiver = new BufferedFileReceiver();
fileReceiver.setRootPath("");                // !rft chdir 可改
fileServer = new ParallelFileServer(1035, fileReceiver);
fileReceiver.setTaskEvent(new FileReceiveEvent());
```

**接收回调**（`FileReceiveEvent`）：
- 文件保存：`rootPath + savePath + fileName`
- 若是 `.png` / `.wav`（且不是带 `quiet` 标志的）：
  - 文件名中 `MASK` 字符串会被剥离（例：`audio.wMASKav` → `audio.wav`）
  - 生成 URL：`http://<host>/ghost/<root>/<save>/<file>`
  - 推送给所有 `screenShot` 属性的 Master

### 8.3 HTTP 取回

## 10. 已知问题与改进方向

### 10.1 协议层

- **明文密码 + 无 TLS**：`master.pw=000112` 是明文存储，传输也是明文 TCP。任何监听者都能拦截。
- **无消息长度前缀**：单一字符 `!` / `\n` 作为分隔符，遇到含 `!` 的文本就会被截断。`FuncRFT` 内已经因为这个用 `*` 转义 `!`，是 patch 而非根治。
- **编码混用历史**：UTF-8 / GBK 在不同位置切换，最新 commit 已经把 Client 简化为不转换，但 Server / Master 仍是 GBK。

### 10.2 服务端

- `TransCmd.handleCommand()` 是单一 switch 块，几百行难以维护。可以拆为策略模式（仿 Client）：每个 `!cmd` 对应一个 `ServerFunc`。
- `server_old` 命名暗示有 `server_new` 计划，但 `META-INF/server_new/` 是空壳，重构未真正开始。
- `Check*Alive` 类有 5 个，命名近似（CheckAliveTimer / CheckConnAlive / CheckAliveMaster / CheckMasterAlive / CheckAliveTimer），职责区分需要看注释才知道，可合并 / 重命名。

### 10.3 控制端

- README 自承"可读性低，待重构"。GUI 与网络层耦合较紧（`MasterMain` 暴露大量 `public static`，被 GUI 直接访问）。
- `InitGUI` 是 920+ 行的大类，承担所有组件装配。建议拆分为面板级 Builder。
- 控制台输出无颜色 / 无搜索 / 无过滤。

### 10.4 客户端

- 已是三端中质量最高的，但仍有几个点：
  - `FuncDefault` 兜底逻辑可能让运维者意外把控制指令打到子进程里，建议在 Processor 显式区分"未知指令"和"透传"两种模式。
  - `ScreenSniffer` 的位移阈值硬编码 10px、20s 周期硬编码。
  - `FuncRFTX` 是空壳。

### 10.5 安全性

> 项目本身就是"演示远控协议",所以这部分不是"修就好"——而是写文档时要让读者认识到：

- 没有任何身份认证（除了 Master 端的明文密码），任何能连到 1033 端口的进程都可以冒充 Client。
- Client 不验证 Server 身份，存在 MITM 风险。
- 文件接收 `FileManager.changeDir()` 仅做了 `..` 的一层保护，需要审计是否能逃逸 RFT 根目录。
- `!ban` 是事后封禁，不能防 DDoS 级别的连接洪水。

### 10.6 可重构的优先级建议

| 优先级 | 目标 | 收益 |
|---|---|---|
| P0 | 把 `TransCmd` 拆成策略模式 | 大幅降低改 Server 指令的成本 |
| P1 | 引入消息长度前缀 + 二进制帧 | 消除 `!` 转义、`?` 转义等 patch |
| P1 | 统一 Server / Master / Client 的 Out / Config / FileRW 工具类（目前三端各有一份） | 减少重复代码 ~30% |
| P2 | Master GUI 拆分 | 降低 InitGUI 复杂度 |
| P2 | TLS / 握手认证 | 安全性 |
| P3 | RFTX 实现 / 移除 | 消除半成品代码 |
